## 1. Summary

`omnigraph studio` opens a browser UI over one graph: a sidebar of node and edge types with row counts, a data grid per type, the schema source, and the branch and commit the view is pinned to. The UI is static files embedded in the `omnigraph` binary and served by the CLI process on a loopback port. It talks only to the documented `/graphs/{id}/…` HTTP API.

The command has two modes. **Boot mode** (`--cluster <dir>`) runs `omnigraph-server` in-process against a local cluster folder, for development. **Attach mode** (`--server <name|url>`) proxies to a server that is already running, for a live cluster. In both modes the bearer token stays in the CLI process and the browser only ever talks to loopback.

What does not change: the `omnigraph-server` binary, its wire surface, `openapi.json`, authorization, and the single-writer rule. The server crate gains one public seam, a way to mount extra routes on the app it already builds, and nothing else.

## 2. Motivation

Today the only ways to look at a graph are the CLI's table output and Tower, ModernRelay's hosted console. The CLI is fine for one query and poor for orientation: which types exist, how many rows each has, what a row looks like, what changed in the last commit. Tower answers those questions but needs an account, a registered cluster, and a reachable endpoint, so it does not serve the developer with a cluster folder on a laptop, the case the quickstart and `cluster apply` docs are written for.

Comparable database tools ship this as a CLI-launched local UI: `drizzle-kit studio`, `prisma studio`, `pgweb`, and the dashboards bundled with Meilisearch and Qdrant (section 8). The pattern is proven and the expectation is set. A local UI is also the cheapest way to show branches and commits, the feature that distinguishes OmniGraph, to someone evaluating it.

Why an RFC and not a PR: it adds a CLI contract, a JavaScript build step to a Rust-only repository, and a public seam in the server crate. Those are three decisions that are costly to walk back once users depend on the command.

## 3. User and operational behavior

```bash
# Development: boot a private server on a loopback port and open the browser.
omnigraph studio --cluster ./company-brain

# A live cluster: attach to the running server with the stored credential.
omnigraph login prod --token …          # existing command
omnigraph studio --server prod --graph knowledge
```

Flags: `--cluster <dir>` or `--server <name|url>` (exactly one); `--graph <id>` selects the graph to open (optional; the UI lists the graphs the credential can see); `--bind <addr>` defaults to `127.0.0.1:0`, a free port, and refuses a non-loopback address; `--no-open` prints the URL instead of opening a browser; `--as <actor>` names the actor for boot-mode commits and defaults to `act-studio`.

Boot mode starts the server the way `omnigraph-server --cluster <dir> --unauthenticated` would, on loopback only. The cluster must be applied; an unapplied folder gets the same `cluster_state_missing` error the server gives. Boot mode is for a folder nobody else is serving. OmniGraph allows one writer per cluster, so booting the studio against a folder a production server already serves is an operator error, exactly as running a second `omnigraph-server` would be. The command says so in its help and in the startup banner. Attach mode is the supported way to look at a served cluster.

Attach mode resolves the server and credential exactly as `omnigraph query --server` does today, including `~/.omnigraph/config.yaml` and `login`. The CLI process forwards `/graphs/*`, `/healthz` and `/readyz` to the remote with the `Authorization` header added. Policy is enforced by the remote server as for any client; the studio has no permission of its own. A `GET /graphs` denial shows as an empty graph list with the server's error, not as a studio failure.

The UI is served at `/` with assets under `/_studio/`. Those routes carry no authentication: they are static files, and the socket is loopback. Everything the UI reads or writes goes through the existing authenticated graph routes on the same origin.

The studio reads with inline GQ through `POST /graphs/{id}/query`, one generated query per type and page, and shows the `graph_commit_id` the rows were read at. Phase 1 is read-only. Writes, when they come, use `/mutate/if-graph-commit` with that commit so a stale grid cannot overwrite a newer head.

Stopping the CLI stops everything. The studio keeps no state of its own on disk.

## 4. Design

**Crates.** A new crate `crates/omnigraph-studio` owns the UI source (`ui/`, Vite + React + TypeScript) and exports one `axum::Router` that serves the built assets from `include_dir!("ui/dist")`. `omnigraph-cli` gains the `studio` subcommand; it already depends on `omnigraph-server`, `omnigraph-cluster` and `reqwest`, so boot and attach need no new dependencies there. `omnigraph-server` gains `serve_with_routes(config, extra: Router)`; `serve(config)` becomes `serve_with_routes(config, Router::new())`. The extra routes are merged after the server's own, so a server route always wins. The `omnigraph-server` binary does not use the seam.

**Built assets are committed.** `ui/dist` is checked in, the same way `openapi.json` is: the Rust build never runs JavaScript, `cargo build --locked` works on a clean checkout, and CI rebuilds the UI with a pinned Bun and fails if the committed `dist` differs. The UI's own checks (type check, unit tests for the schema parser) run in that same CI job. Contributors who do not touch the UI never need Bun. This adds about 0.5 to 1 MB to the `omnigraph` binary. Section 8 records how comparable projects decided this.

**Everything the UI knows comes from the HTTP API.** Types and properties are parsed in the browser from the `schema_source` that `GET /graphs/{id}/schema` returns, with a small TypeScript parser for the `.pg` grammar. Row counts come from `GET /snapshot`, branches from `GET /branches`, history from `GET /commits`, rows from `POST /query`. There is no studio-only endpoint and no filesystem access from the UI, so attach mode and boot mode run the same UI code. A sidebar folder is a UI convention: a line comment of the form `// 1 — Organization` before a group of declarations opens a folder of that name. It changes nothing in the schema language and is ignored by everything else.

**Implementation plans.** Four files under `assets/2026-10-02-studio/` carry the detail that does not belong in the decision record: [the server seam](assets/2026-10-02-studio/01-server-seam.md), [the `studio` subcommand](assets/2026-10-02-studio/02-cli-subcommand.md), [the crate and the UI](assets/2026-10-02-studio/03-studio-crate-and-ui.md), and [build, CI and release](assets/2026-10-02-studio/04-build-ci-and-release.md). They are plans, not contracts; this RFC is the contract.

**Request path.** Boot mode: browser → loopback → in-process axum app (studio routes merged with the server's) → engine. Attach mode: browser → loopback → CLI reverse proxy → remote server. The proxy forwards method, path, query string, body and content-type, adds `Authorization`, strips hop-by-hop headers, and returns the remote status and body unchanged, so errors reach the UI exactly as the server wrote them.

## 5. Invariants

- **Invariant 10, trust at the boundary.** Unchanged. The browser never holds a token and never names an actor. In attach mode the remote resolves the token to an actor as it does for the CLI today. In boot mode the in-process server runs in the existing `Open` runtime state, which the server already permits only with an explicit opt-in, and the studio adds the stronger condition that the socket is loopback. `--as` is the same operator-side actor selection that direct-engine writes use.
- **Invariant 11, bounded resource use.** Boot mode inherits the server's body limit and admission limits because it is the server. The attach proxy adds one bound of its own: a request timeout, and it streams bodies rather than buffering them.
- **Invariant 3, one coherent view.** Every grid shows the `graph_commit_id` it was read at; a later write path must use the conditional mutation route with that id.
- **Deny-list.** No item is touched. The studio adds no storage primitive, no engine access outside the HTTP routes, no parallel truth, and no silent retry: a failed request is shown with the server's status and error body.

## 6. Compatibility and reversibility

The `omnigraph-server` wire surface and `openapi.json` are unchanged; the UI routes exist only in a process that mounted them, and the OpenAPI test keeps passing because they are not part of the documented API. Storage is untouched. The CLI gains one subcommand and grows by the embedded assets. Reverting is deleting one crate, one subcommand, one CI job and one public function; nothing on disk or on the wire depends on the studio having existed.

Support boundary: the studio tracks the server version it is built with. Attach mode against an older server degrades per route, since the UI shows the server's error for a route the server lacks and never falls back to another route, in line with the conditional-mutation rule in the server docs.

## 7. Alternatives

- **Do nothing; point users at Tower.** Tower is hosted, needs an org, a registered cluster and a reachable endpoint, and cannot see a laptop cluster folder. It also lives in a private repository. It is the right answer for a team console and the wrong one for the quickstart.
- **Hosted UI, local server (the Drizzle model).** `omnigraph studio` would only open `studio.omnigraph.dev`, which connects to localhost. No JavaScript in this repository, but it needs a domain and deployment the project would have to run, CORS on the server, the token in the browser, and a network connection. It also breaks the moment the hosted UI and the local server disagree on a version.
- **A separate repository and runtime (a Bun or Node package).** Keeps the Rust build untouched, but a second process has to proxy to the server anyway because the server sends no CORS headers, the published crates stop at 0.8.0 so it cannot embed the server, and users get a second toolchain to install for a command that belongs next to `omnigraph query`.
- **Separate UI repository, downloaded at build time (the Meilisearch pattern).** `build.rs` fetches a release zip pinned by URL and checksum and embeds it. No JavaScript in this repository and no committed assets, at the cost of a network fetch inside `cargo build --locked`, a second repository to release in lockstep, and a feature flag so offline builds still compile. This is the fallback if committed assets are refused. Qdrant's variant, downloading after the build and serving from disk, leaves `cargo install` and `install-source.sh` users without a UI.
- **Build the UI inside `cargo build` with a local Bun step.** Makes every contributor install Bun. Committing `dist` with a drift check is the same guarantee with none of that.
- **No server seam: the studio always proxies.** Boot mode would start the in-process server on its own loopback port and the CLI would run a second listener that serves the UI and proxies to it, exactly as attach mode does. Zero changes to `omnigraph-server`, one extra loopback hop per request, and two ports instead of one. Acceptable if maintainers prefer the server crate untouched; the UI and the CLI code are the same either way.
- **Add CORS to `omnigraph-server` instead of a proxy.** Puts the token in the browser and widens the production server's surface for a development feature. The proxy is a few dozen lines in a process that already has the credential.

## 8. Prior art

How comparable tools ship a CLI-launched database UI, checked against their repositories on 2026-10-02.

| Tool | UI source | Built assets | How the binary gets them |
|---|---|---|---|
| Meilisearch (Rust) | Separate repo, `meilisearch/mini-dashboard` | Not committed | `build.rs` downloads a release zip pinned by URL and SHA-1 in `Cargo.toml`, embeds it with `static-files`; default feature, so an offline build needs `--no-default-features` |
| Qdrant (Rust) | Separate repo, `qdrant/qdrant-web-ui` | Not committed | A shell script downloads the latest release zip after `cargo build` into `./static`; served from disk, not embedded; a plain `cargo build` has no UI |
| pgweb (Go) | Same repo, hand-written JS plus vendored libraries | Committed | `go:embed`; no JavaScript build step at all |
| Prisma Studio | Closed | Shipped inside the `prisma` npm package | Served by the local CLI process on `localhost:5555` |
| Drizzle Studio | Closed | Hosted at `local.drizzle.studio` | `drizzle-kit studio` runs a local server; the hosted page connects to it |

Two patterns cover the Rust projects: a separate UI repository whose release is downloaded at build time (Meilisearch) or after it (Qdrant). Neither commits built assets, and neither gives a plain offline `cargo build` the UI. pgweb is the only one with committed assets, and it avoids a build step by writing plain JavaScript. This RFC proposes committed built assets with a drift check, which none of them do, because this repository's release builds are `cargo build --locked` with no network and `install-source.sh` is a supported install path. The Meilisearch pattern is the closest fallback and is listed in section 7.

## 9. Evidence and tests

- `crates/omnigraph-server/tests/`: a new test that `serve_with_routes` serves `/` from the extra router while every existing route and the auth middleware behave as before; `openapi.rs` must keep passing unchanged, which proves the documented surface did not move.
- `crates/omnigraph-cli/tests/`: a new `cli_studio.rs` on the existing `support` fixtures. Boot mode: an applied folder serves `/` and `/graphs`, a non-loopback `--bind` is refused, an unapplied folder fails with `cluster_state_missing`. Attach mode: against a `support`-booted server with a token, the proxy forwards status, body and the `Authorization` header, and the browser-facing socket never sees the token.
- UI: unit tests for the `.pg` parser against every construct in `docs/user/schema/index.md`, and one end-to-end run that boots the demo cluster, loads the seed, and asserts the sidebar counts match `/snapshot`.
- CI: a `studio-ui` job that installs Bun by pinned version, runs the UI checks, rebuilds `ui/dist`, and fails on a diff.
- Acceptance threshold for phase 1: against the Lumen demo cluster (11 node types, 18 edge types, about 1,900 entities) the data grid renders a page of 50 rows in under 100 ms of server time, as reported by the `/query` timing the UI already shows.

## 10. Rollout

1. **Seam and skeleton.** `serve_with_routes` in `omnigraph-server`, the `omnigraph-studio` crate with a placeholder page, the `studio` subcommand with boot mode only. Ships as a hidden subcommand. Nothing user-visible changes.
2. **Phase 1 UI.** Sidebar with folders and counts, data grid with paging and client-side search, schema source view, header with branch, head commit, branch count and commit count. Attach mode. The subcommand becomes visible and documented in `docs/user/cli/`. `implementation` moves to `partial`.
3. **Phase 2.** Record page with neighbours, branch switching, commit history with per-commit changes from `/commits/{id}/changes`. `implementation` moves to `complete` for this RFC; edits are a separate RFC because they need a conflict story.

Each step is independently shippable and revertible.

## 11. Unresolved questions

- Does commit attribution in the server's `Open` runtime state already produce a usable actor id, or does boot mode need `--as` to feed the server config? If the former, drop `--as`.
- Is a sidebar folder convention over comments acceptable, or do maintainers prefer a formal schema annotation such as `@section("Organization")` later? Phase 1 works either way.
- Is there a serving lock the studio can check to refuse boot mode on a folder another server already serves, or does the documented operator responsibility stand?
- Bun or Node for the pinned UI toolchain in CI. The code is identical; this is a maintainer preference.
